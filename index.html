Caderno de Exercícios: SQL

Prática de Constraints, Integridade Relacional e Modelagem de Dados

⚠️ Atenção: Formato de Entrega A entrega desta atividade deverá ser feita exclusivamente através de um arquivo .sql contendo todos os scripts de resolução numerados. Use este material online apenas como referência para leitura das questões.

Parte 1: Criação de Estruturas e Regras

1. Criar tabela com NOT NULL Questão 1
Contexto: Em um sistema de cadastro de clientes de uma clínica médica, não faz sentido ter registros sem nome ou e-mail. O NOT NULL garante que informações essenciais nunca fiquem em branco, evitando problemas em agendamentos e comunicações.
2. Criar coluna com UNIQUE Questão 2
Contexto: Em um sistema de login de uma plataforma de cursos online, cada usuário precisa ter um e-mail único para autenticação. O UNIQUE evita duplicidade e garante que cada conta seja exclusiva.
3. Criar campo com DEFAULT Questão 3
Contexto: Em um sistema de pedidos de e-commerce, se o status não for informado, deve começar como 'aberto'. O DEFAULT automatiza essa regra e garante consistência no fluxo de pedidos.
4. Criar constraint com CHECK Questão 4
Contexto: Em um sistema de estoque de supermercado, não faz sentido cadastrar produtos com preço negativo. O CHECK impede erros de digitação e protege contra dados inválidos que poderiam comprometer relatórios financeiros.
5. Criar FOREIGN KEY Questão 5
Contexto: Em um sistema de RH, cada funcionário pertence a um departamento. A FOREIGN KEY garante que não existam funcionários vinculados a departamentos inexistentes, mantendo a integridade organizacional.
6. Criar FOREIGN KEY com ON DELETE CASCADE Questão 6
Contexto: Em um sistema escolar, se uma turma for excluída, todos os alunos vinculados a ela também devem ser removidos automaticamente. O CASCADE evita registros “órfãos” e mantém o banco limpo.
7. Criar FOREIGN KEY com ON DELETE RESTRICT Questão 7
Contexto: Em um sistema de gestão hospitalar, não é permitido excluir um médico enquanto houver pacientes vinculados a ele. O RESTRICT protege contra exclusões indevidas que poderiam comprometer o histórico clínico.
8. Criar chave primária composta Questão 8
Contexto: Em um sistema de vendas, um mesmo produto pode aparecer em vários pedidos, mas dentro de um mesmo pedido não pode se repetir. A PK composta garante essa regra de negócio.
9. Criar constraint nomeada Questão 9
Contexto: Em sistemas grandes de bancos ou seguradoras, nomear constraints facilita manutenção. Se um erro ocorrer, o banco mostra o nome da constraint, ajudando a identificar rapidamente o problema sem confusão.
10. Criar tabelas completas na ordem correta e organizar SQL Questão 10
Contexto: Imagine um sistema de e-commerce que precisa controlar clientes, pedidos, produtos e itens de pedido. Para que o banco funcione corretamente, é essencial criar as tabelas na ordem certa (primeiro as “tabelas pai”, depois as “filhas”) e manter o SQL organizado. Em empresas reais, scripts desorganizados podem gerar erros de integridade e dificultar a manutenção. ORGANIZE O SQL ABAIXO:
CREATE TABLE pedidos (status VARCHAR(20) DEFAULT 'aberto', id INT PRIMARY KEY, cliente_id INT, FOREIGN KEY (cliente_id) REFERENCES clientes(id)); CREATE TABLE clientes (email VARCHAR(255) UNIQUE, id INT PRIMARY KEY, nome VARCHAR(100) NOT NULL); CREATE TABLE produtos (preco DECIMAL(10,2), id INT PRIMARY KEY, CONSTRAINT ck_preco CHECK (preco >= 0), nome VARCHAR(100) NOT NULL); CREATE TABLE pedido_item (quantidade INT NOT NULL, produto_id INT, pedido_id INT, PRIMARY KEY (pedido_id, produto_id), FOREIGN KEY (produto_id) REFERENCES produtos(id), FOREIGN KEY (pedido_id) REFERENCES pedidos(id));

Parte 2: Exercícios com Múltiplas Tabelas e Contextos

11. Tabela Clientes Questão 11
Contexto: Em um sistema de e-commerce, os clientes precisam ter dados básicos de identificação e contato.
Particularidades: Cada cliente deve ter um identificador único, não pode existir cliente sem nome ou e-mail, e o e-mail não pode se repetir entre diferentes clientes.
12. Tabela Produtos Questão 12
Contexto: Produtos vendidos precisam ter informações consistentes para controle de estoque e vendas.
Particularidades: Cada produto deve ter um identificador único, não pode existir produto sem nome, o preço deve seguir uma regra de negócio (não pode ser inválido), e o status inicial deve ser definido automaticamente.
13. Tabela Pedidos Questão 13
Contexto: Cada pedido pertence a um cliente e precisa registrar informações essenciais.
Particularidades: Deve haver ligação com a tabela de clientes, todo pedido precisa ter uma data de criação obrigatória, e o status deve começar com um valor padrão.
14. Tabela Pedido_Item Questão 14
Contexto: Um pedido pode ter vários produtos, mas o mesmo produto não pode se repetir dentro do mesmo pedido.
Particularidades: Precisa de uma chave composta para identificar corretamente cada item, deve estar ligado tanto à tabela de pedidos quanto à de produtos, e a quantidade precisa seguir uma regra de negócio (não pode ser inválida).
15. Tabela Departamentos Questão 15
Contexto: Em um sistema de RH, os funcionários precisam estar vinculados a departamentos válidos.
Particularidades: Cada departamento deve ter um identificador único, não pode existir departamento sem nome, e o nome não pode se repetir.
16. Tabela Funcionarios Questão 16
Contexto: Cada funcionário pertence a um departamento e precisa estar corretamente vinculado.
Particularidades: Deve haver ligação com a tabela de departamentos, a exclusão de departamentos precisa ter uma regra clara (se pode ou não excluir quando há funcionários), e as restrições devem ser nomeadas para facilitar manutenção.
